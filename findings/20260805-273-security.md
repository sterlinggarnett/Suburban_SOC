## HIGH — the audit trail overclaims what the credential can prove

**T1078 (Valid Accounts).** `/approve` and `/webhook/dispatch` are gated by the *same*
`HIVE_MIND_SECRET` (`app.py:45`; both call `_verify_and_parse` at `:319` and `:382`). The agent
container holds that secret to sign `/webhook/dispatch`. Nothing stops that container — or an
attacker who extracted the secret from it — from instead signing `/approve` for an `id` read from
`/pending`. The broker cannot distinguish the two callers and records
`"approver": "broker-operator"` (`:388`), the label that signifies a human clicked approve.

The fix narrows forgery from *any string* to *one of two fixed labels selected by URL*. It does not
restore §12.3's human-in-the-loop guarantee.

`app.py:73-74` is honest about this in a comment, but the `/approve` docstring still asserts
`"""Human-of-record approves a drafted block..."""` (`:376`), and `docker-compose.yml:559-560`
says only the agent can reach `/webhook/dispatch` without noting the same holder reaches
`/approve`. No success row records the caller IP (only `write_denial()` captures
`request.client.host`), so there is no network-origin signal to cross-check an `/approve` row.

**Contrast with #246**, which this issue claims to mirror: that fix used a *second, independent
secret* (`SOC_APPROVER_HMAC_SECRET`) never given to the input-facing container, plus
`_resolve_approver_secret()`'s same-secret-collision detection (`agent.py:158-179`). The broker fix
replicates the label half of #246, not the credential-separation half.

**Remediation:** add `BROKER_APPROVER_HMAC_SECRET`, provisioned only to whatever signs human
`/approve` calls and never to the agent container, mirroring the collision detection; gate
`/approve` + `/pending` on it. Until then, stop the docstring and compose comment from
overclaiming, and carry this as a documented residual risk.

## MEDIUM — `/approve` discards the caller's claim, so the highest-trust endpoint has the weakest trail

`/webhook/dispatch` deliberately keeps a mismatched `approver` as `upstream_approver_claimed`
(`app.py:331`) because a value other than the expected literal signals a hand-crafted payload.
`/approve` has no equivalent — `body.get("approver")` is never read (`:382-390`) — so a suspicious
`/approve` payload leaves no trace at all, on the endpoint the fix exists to protect.

**Remediation:** call `_claimed_approver(body)` in `approve()` and attach the field to all four
write paths (`:403-404`, `:408-409`, `:416-417`, `:421-423`).

## MEDIUM — nothing consumes `upstream_approver_claimed`

`approval_queue.jsonl` is shipped to Elasticsearch by no Filebeat/Logstash config under `configs/`.
`/pending` never exposes resolved rows (`app.py:368-370`), and `compact_broker_approval_queue.py`
is schema-agnostic (`id`/`status`/`ts` only). No dashboard, Watcher, or rule reads the field,
despite the stated intent that a mismatch is "worth seeing."

**Remediation:** ship resolved/executed rows to `soc-audit-*` alongside `write_denial()`'s docs, or
add a scheduled check (next to the compaction cron) that flags any claim != `"soc-ai-agent"`.

## LOW — claim string is length-bounded but not character-filtered

`_claimed_approver()` (`app.py:98-103`) truncates to 64 chars with no control-char / bidi-override
(U+202E) / ANSI-escape filtering. `json.dumps`'s `ensure_ascii=True` default prevents JSONL line
injection today, so this is latent rather than live — but it should be closed before a consumer
that renders the string is added, not after.

**Remediation:** strip Unicode categories Cc/Cf before truncation.
