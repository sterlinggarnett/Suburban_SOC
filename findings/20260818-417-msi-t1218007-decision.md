# #417 — MSI/Word Zeek-indistinguishability: documented decision

## Scope

`net_zeek_executable_download.yml`'s own description already disclosed (from
#384's live-fire sweep) that a real MSI installer types identically to a
genuine Word document at the Zeek files.log logsource — both share the OLE
Compound File Binary magic (`\xd0\xcf\x11\xe0\xa1\xb1\x1a\xe1`), and Zeek's
own signature source (`base/frameworks/files/magic/office.sig`) acknowledges
this ambiguity in its own comment ("non-specific and terrible but ... there
doesn't seem to be a better option"). The disclosure ended with "Filed as
#417" but never recorded what happened next — #417 asked for that decision
to actually be made and written down.

## Decision

**Not pursued at the network logsource.** mime_type filtering structurally
cannot discriminate an MSI from a Word document here — adding
`application/msword` to the mime_type list would flag every legitimate
Word-document download or email attachment with zero ability to tell the
malicious case apart. A correlation-based approach (source-reputation- or
threat-intel-gated `application/msword` alerting, suggested as an option in
#417) was judged not worth the added tuning/false-positive surface, because
a better option already exists.

**T1218.007 is already covered at the endpoint logsource**, by
`rules/sigma/proc_creation_win_msiexec_remote.yml` (Sysmon process_creation:
`msiexec.exe` with an install verb directly adjacent to an `http(s)` URL) —
the "more tractable" option #417 itself suggested. This rule predates #417
and was not written in response to it; the only gap was that nothing
cross-referenced it as the answer to the network-logsource limitation.

## Fix

- `rules/sigma/net_zeek_executable_download.yml`: closed the open "filed as
  #417" thread with the decision above and the cross-reference to
  `proc_creation_win_msiexec_remote.yml`.
- `rules/sigma/proc_creation_win_msiexec_remote.yml`: added a reciprocal
  note explaining it's the endpoint-side answer to this network-logsource
  blind spot, so the connection is discoverable from either rule.

No detection logic, `mime_type` list, tags, or `level` changed on either
rule — description-only. Confirmed via
`tests/detections/test_sigma_detections.py::...share_the_exact_same_mime_type_list`
(still passes; it only checks the `mime_type` array) and the full
`pytest tests/` run (955 passed, only the `sigma`-CLI-dependent
`test_live_fire.py` excluded — pre-existing, unrelated to this environment).
