## Must-Fix

1. **`test_app.py:520` (`test_identity_falls_back_when_env_var_set_but_empty`) is vacuous — it never exercises `app.py`'s actual code.**
   The test body is:
   ```python
   monkeypatch.setenv("BROKER_APPROVER_IDENTITY", "")
   monkeypatch.setenv("BROKER_DISPATCH_IDENTITY", "")
   assert (os.getenv("BROKER_APPROVER_IDENTITY") or "broker-operator") == "broker-operator"
   assert (os.getenv("BROKER_DISPATCH_IDENTITY") or "soc-ai-agent") == "soc-ai-agent"
   ```
   It re-implements the `or`-fallback expression inline rather than asserting
   on `broker_app.APPROVER_IDENTITY` / `broker_app.DISPATCH_IDENTITY`. I
   confirmed this experimentally: reverting `app.py:86-87` to the buggy
   two-arg form (`os.getenv("BROKER_APPROVER_IDENTITY", "broker-operator")`
   — the exact defect #246's review caught, which this test's own docstring
   cites) leaves this test passing (`1 passed`). It cannot fail no matter
   what `app.py` does, because it never imports the value it claims to
   verify.
   Root cause: `APPROVER_IDENTITY`/`DISPATCH_IDENTITY` are computed once at
   module-import time (`app.py:86-87`), so `monkeypatch.setenv` after import
   has no effect on them without a reload — which is presumably *why* the
   test was written to duplicate the expression instead of asserting on the
   real constant.
   **Fix:** either (a) `importlib.reload(broker_app)` inside the test after
   setting the env vars and assert on the reloaded module's
   `APPROVER_IDENTITY`/`DISPATCH_IDENTITY` (restoring the original env/module
   state afterward so it doesn't leak into other tests), or (b) factor the
   resolution into a small pure function — e.g. `_resolve_identity(env_key,
   default)` — mirroring agent.py's `_resolve_approver_secret` pattern, and
   unit-test *that* function directly with an explicit env dict, independent
   of module import order.

2. **`test_app.py:502` (`test_dispatch_without_approver_records_no_claim`) passes against the reverted vulnerable code too — it is not a false-positive-proof regression test for the credential-binding property.**
   Confirmed by the same experiment (reverting only `dispatch_block`'s
   `approver = DISPATCH_IDENTITY` / `claimed_approver` lines back to
   `approver = str(payload.get("approver", "soc-ai-agent"))`): this test
   still passes, because with no `approver` field in the request the old
   *and* new code both resolve to the literal string `"soc-ai-agent"` — the
   assertion `row["approver"] == broker_app.DISPATCH_IDENTITY` is true by
   coincidence (default env, default literal), not because the row is
   provably credential-bound. It does correctly cover the "absent field →
   no `upstream_approver_claimed` key" behavior, so it isn't *entirely*
   worthless — but the "bound identity" half of its name/docstring is not
   actually verified.
   **Fix:** set `BROKER_DISPATCH_IDENTITY` (via monkeypatch + reload, per
   finding 1) to a value that differs from the hardcoded `"soc-ai-agent"`
   literal before this test runs, so the assertion can only pass if
   `dispatch_block` is reading the configured identity rather than falling
   through to the old body-controlled default.

   Net effect of the two findings above: **4 of the 6 new tests are
   genuinely mutation-proof** (`test_approve_ignores_body_supplied_approver`,
   `test_approve_denial_rows_also_record_bound_identity`,
   `test_dispatch_records_bound_identity_and_labels_upstream_claim`,
   `test_claimed_approver_is_bounded` — all verified to fail against the
   reverted code), **2 are not** (findings 1–2 above). This matches what you
   flagged going in.

## Should-Fix

3. **`upstream_approver_claimed` is currently a write-only field — no code in the repo reads it.**
   `grep -rn "upstream_approver_claimed"` outside `app.py`/`test_app.py`
   returns nothing: no Watcher/detection rule, no dashboard, and
   `compact_broker_approval_queue.py` (`scripts/hive-mind-broker/compact_broker_approval_queue.py`)
   only classifies by `status`, never inspects this field. The stated
   rationale (`app.py:89-94`, "a value that is anything OTHER than the
   expected literal ... is worth seeing in the audit trail") is honest about
   scope — it's a passive audit record for manual `grep`/review of
   `approval_queue.jsonl`, not an active detection — and the implementation
   cost is genuinely small (~10 lines, bounded, reuses the existing
   `_verify_and_parse`d payload). I don't think this is meaningful YAGNI
   over-building; it's cheap and consistent with the file's existing
   audit-log conventions (e.g. `result` is also captured without being
   consumed by automation). But as written, its value is 100% latent until
   someone (a) manually greps the queue, or (b) a follow-up wires a
   detection rule comparing `upstream_approver_claimed` against the
   `DISPATCH_IDENTITY` literal.
   **Fix (optional, not blocking):** file a short follow-up issue for a
   detection/alert on `upstream_approver_claimed != "soc-ai-agent"` in
   `soc-audit-*`/Kibana, or note in the comment that realizing this value
   today requires manual review of `approval_queue.jsonl` rather than
   implying it's actively monitored.

4. **`_claimed_approver()` (`app.py:98-103`) stringifies non-string JSON types with Python `repr`-style formatting, not JSON.**
   ```python
   def _claimed_approver(payload: dict):
       raw = payload.get("approver")
       if raw is None:
           return None
       return str(raw)[:_CLAIMED_APPROVER_MAX]
   ```
   If a caller sends `"approver": {"x": 1}` or `["a","b"]` (both valid JSON,
   and the caller is anyone holding `HIVE_MIND_SECRET`, which is exactly the
   population this field exists to make visible), `str(raw)` renders Python
   syntax (`"{'x': 1}"`), not JSON. Not a security issue — `_append_action`
   still `json.dumps()`s the whole record before writing, so no injection
   into the JSONL structure — but it's a rough edge for whoever reads the
   audit trail (looks like malformed JSON, not like a deliberate label). No
   test exercises this path.
   **Fix:** either restrict to `str` (`return str(raw)[:_CLAIMED_APPROVER_MAX]
   if isinstance(raw, str) else f"<non-string:{type(raw).__name__}>"`) or
   explicitly document that non-string claims are stringified via `repr`-like
   conversion and add one test locking down the behavior either way.

## Nice-to-Have

5. **`app.py:98` `_claimed_approver(payload: dict):` has no return-type annotation.**
   The rest of the file is inconsistent on this already (`_append_action(action: dict) -> None` is annotated, `safe_tenant(value):` is not), so this isn't a new inconsistency, but since the function's only interesting property is "returns `str | None`," a `-> str | None` annotation would make that contract explicit at the call site in `dispatch_block` (`app.py:331`).

6. **`_CLAIMED_APPROVER_MAX = 64` (`app.py:95`) has no stated rationale for the specific number.** Every other bound/threshold in this file that isn't self-evident gets a one-line "why" (see `HMAC_REPLAY_WINDOW`, `_TENANT_RE`). 64 is a reasonable, generous bound for a display label, but a half-line ("long enough for any real analyst name/handle, short enough to bound a hostile payload") would match house style.

7. **`app.py:330-331`** — `claimed_approver = _claimed_approver(payload)` is computed before the exclusion (`app.py:334`) and no-routers early returns, both of which discard it unused (neither branch calls `_append_action`). Harmless (cheap string slice, and it mirrors the pre-fix code's existing ordering of the `approver` assignment), but if touched again, computing it just before the `_append_action` call at `app.py:348-354` would save a wasted call on the two early-return paths.

## Correctness walkthrough (no findings — confirmed clean)

- **`approve()` (`app.py:374-426`):** `approver = APPROVER_IDENTITY` is set once, immediately after the body is parsed and before any of the four `_append_action` call sites (three denial paths — invalid `attacker_ip` at `app.py:403-404`, exclusion at `app.py:408-409`, no-routers at `app.py:416-417` — plus the success path at `app.py:421-423`). Every path that writes a queue row has `approver` defined and identity-bound; none can write `"approver": "unknown"` or a body-supplied value anymore.
- **`dispatch_block()` (`app.py:305-361`):** the exclusion (`app.py:334-337`) and no-routers (`app.py:341-345`) early returns write **no** queue row at all (matches the pre-existing `/webhook/alert` convention of the same two guards) — so there's no path that writes a row with a missing/wrong approver; those branches just don't audit, which is out of #273's scope and not a regression.
- **Two-env-var split (`APPROVER_IDENTITY` vs. `DISPATCH_IDENTITY`) earns its keep.** Both are gated by the same `HIVE_MIND_SECRET`, but they label two different real-world callers (a human at `/approve` vs. the agent at `/webhook/dispatch`) that an operator may reasonably want distinguishable in the audit trail (e.g. a compliance reviewer scanning `approval_queue.jsonl` for which rows were human-approved vs. agent-dispatched) — collapsing to one var would make every row say the same label regardless of endpoint, defeating that. This mirrors the agent's own two-secret split for the same class of problem (`SOC_AGENT_HMAC_SECRET` vs. `SOC_APPROVER_HMAC_SECRET`, `agent.py:45,178-179`).
- **Comment accuracy — verified against code, not asserted:**
  - `app.py:63-65` / `.env.example:236` / `docker-compose.yml:257-258` claim `os.getenv(key, default)` only applies the default when the key is absent, and that a set-but-empty var needs `or`. True — confirmed against Python's documented `os.getenv`/`os.environ.get` semantics and reproduced directly (§ Must-Fix 1).
  - `app.py:89-90` claims "today the agent sends the fixed literal `soc-ai-agent`" — confirmed at `scripts/setup/ai_agent/agent.py:335` (`"approver": "soc-ai-agent"` in `dispatch_block_via_broker`).
  - `app.py:65` / test docstrings claim this is "the same defect #246's review caught in the agent's SOC_APPROVER_IDENTITY" — confirmed against commit `2d371c6` ("security: split /approve+/pending HMAC secret from /alert's (#246) (#274)"), whose message explicitly lists "an empty-but-set SOC_APPROVER_IDENTITY falling through past its intended default" as a security-auditor finding on that PR.
  All three factual claims check out.
- **Naming/structure:** `_claimed_approver()` and `_CLAIMED_APPROVER_MAX` sit right after the `#273` config block, ahead of `APPROVAL_QUEUE` — this matches the file's existing precedent of defining small shared helpers (`safe_tenant`, `app.py:115-118`) immediately after the config section, well ahead of their (distant) call sites in the endpoint functions, rather than inline at first use. Consistent with house style, not a smell.
- **Consistency with `agent.py`:** the `#273` comment block (`app.py:70-95`) and `agent.py`'s equivalent (`agent.py:179-187`) are near-identical in structure and the specific `or`-vs-two-arg-default reasoning — the stated "mirrors a pattern established in agent.py" claim holds up line-for-line.

## Verdict

⚠️ **Approve with conditions** — the production code (`app.py`) is correct: every
approve()/dispatch_block() path was traced and none can write a row with a
missing or body-controlled approver, the two-var split is justified, and every
factual claim in the new comments checks out against the code and git history.
The blocking condition is test quality: fix the two vacuous tests (Must-Fix
1–2) before merge, since they exist specifically to prevent regression of a
security fix and two of the six currently provide no such guarantee. The
Should-Fix items (unwired `upstream_approver_claimed`, non-string claim
stringification) are real but not blocking.
