## MAJOR

1. **`tests/ai_agent/test_slo_metrics.py:1854` — new test fails on this exact
   checkout, deterministically, right now.**
   `MainExitCodeTests.test_soc_health_within_target_does_not_breach` calls
   `_mock_all_metrics(soc_health_stale=600.0)` without pinning `coverage=`, so
   `coverage_techniques` keeps `_mock_all_metrics`'s default of `12.0`
   (`tests/ai_agent/test_slo_metrics.py:1558`, `coverage=12.0`). This repo's real
   `scripts/setup/.env` sets `SLO_COVERAGE_MIN=35`
   (`scripts/setup/ai_agent/slo_metrics.py:156`,
   `TARGETS["coverage_techniques"] = float(os.environ.get("SLO_COVERAGE_MIN", "10"))`,
   loaded from `.env` at import time via `env_loader.load_env_file(ENV)` at
   `scripts/setup/ai_agent/slo_metrics.py:144`), so `12.0 < 35.0` breaches on
   `coverage_techniques` and `main()` exits 2, not the 0 the test asserts.
   Reproduced directly:
   ```
   $ python3 -m pytest tests/ai_agent/test_slo_metrics.py -k test_soc_health_within_target_does_not_breach -q
   AssertionError: 2 != 0
   ```
   Every other "exit 0 / does not breach" test added for prior issues in this
   same file explicitly works around this exact local-env quirk by passing
   `coverage=105.0` (see `tests/ai_agent/test_slo_metrics.py:1706`, `:1719`,
   `:1751`, `:1772`, `:1870`, `:1927`, `:1961`, `:1992`, `:2021`, `:2053`, each
   commented "coverage pinned to the real env's SLO_COVERAGE_MIN..."). This new
   test is the one place in the diff that didn't follow that established
   convention. Fix: add `coverage=105.0` to the `_mock_all_metrics(...)` call at
   `tests/ai_agent/test_slo_metrics.py:1858`.
   Note: a second, unrelated failure
   (`PrivilegeSelfCheckMainIntegrationTests::test_precheck_success_does_not_affect_a_healthy_run`)
   was also observed in the full run, but `git show HEAD:tests/ai_agent/test_slo_metrics.py`
   confirms that test already existed pre-diff — it is the same class of local
   drift (MEMORY.md already documents "one slo_metrics test fails only because
   .env SLO_COVERAGE_MIN=35"), not something this changeset introduced, and is
   out of scope for this review.

## MINOR

2. **`configs/systemd/stack-health.service:32-37` — comment says "three
   Environment= lines below," lists only two, and specifically names `ES_USER`
   as one of the values being pinned, but no `Environment=ES_USER=...` line
   exists.**
   ```
   32: # redundant. The three Environment= lines below are the values .env does NOT define
   33: # (verified against this host's .env: no ES_CA/ES_URL/ES_USER key exists), so sourcing
   ...
   36: Environment=ES_URL=https://localhost:9200
   37: Environment=ES_CA=/run/suburban-soc-health/ca.crt
   ```
   Net effect: `stack_health.sh` authenticates to Elasticsearch as whatever
   `ES_USER` `.env` defines, or `es_common.sh`'s default `elastic` superuser
   (`scripts/setup/lib/es_common.sh:53`) if `.env` doesn't set it either — unlike
   `slo-metrics.service` (`ES_USER=slo_metrics`, least-privilege) and
   `intel-refresh.service` (`ES_USER=intel_writer`). This is **not a regression**
   — the pre-existing `stack_health.sh` never overrode `ES_USER` before this
   diff either — but the comment is internally inconsistent in a brand-new file
   and will mislead a future reader into believing `ES_USER` is pinned the way
   `ES_URL`/`ES_CA` are. Either add the missing `Environment=ES_USER=elastic`
   line (making the superuser use explicit and auditable) or fix the comment to
   say "two" and drop the `ES_USER` mention.

3. **`scripts/setup/stack_health.sh:104-106` — the new `soc-slo-metrics`
   freshness check will independently register `slo_metrics` as DOWN during
   *any* Elasticsearch outage, on top of the pre-existing `elasticsearch` DOWN
   entry.** This is explicitly acknowledged in the script's own comment
   (lines 108-111: "the elasticsearch check above is what distinguishes 'ES is
   down' from 'the SLO lane is down'; this line does not guess") so it is a
   documented design choice, not an oversight — but it does mean every ES
   outage now produces two DOWN entries (`elasticsearch`, `slo_metrics`) in the
   same ntfy push instead of one, which is worth knowing when tuning
   alert-fatigue expectations for on-call. Not a functional bug.

## NIT

4. **`scripts/setup/stack_health.sh:91-92` — the `container_up X && check X 0
   ... || check X 1 ...` pattern is the classic "no real if/else" shape**: if
   the `check` call in the `&&` branch itself returned non-zero, the `||`
   branch would *also* fire, double-reporting the component. In practice this
   is dormant: `check()` (`scripts/setup/stack_health.sh:66-68`) always ends on
   a `printf` (`report()`), which essentially never fails, so its return status
   is always 0. This pattern pre-dates the diff (the pre-image had the
   identical shape with `"container down"` instead of `"$(container_detail)"`)
   and is not something this change introduces or worsens — flagging only
   because the task asked to inspect this exact call-site shape.

5. **`tests/pipeline/test_stack_health_unit.py:360-368` —
   `test_soft_mode_call_fails_before_anything_leaves_the_host` doesn't exercise
   any Suburban-SOC code.** It runs `curl --cacert <missing-file>
   https://example.com/` directly and asserts exit code 77, to sanity-check the
   assumption (documented elsewhere in the same test class and in
   `scripts/setup/lib/es_common.sh:83-90`) that a bad `--cacert` path aborts
   curl during SSL setup before any connection is attempted. It's a reasonable
   assumption-check but is environment/curl-build dependent and tests curl's
   behavior, not this repo's. Low value as a regression guard for this
   changeset specifically (an unrelated curl/OpenSSL upgrade could flip it
   independently of any code change here).
