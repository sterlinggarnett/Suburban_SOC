## Gap analysis

### Gap 1 — Sensor + monitor share a failure domain (T1562.001) — P1

**What happens:** Docker Desktop stops. `zeek-host-capture.service` stops
producing logs. `slo-metrics.service`, which computes the metric designed to
notice exactly that, dies at `ExecStartPre` on the dangling
`/usr/bin/docker` symlink (203/EXEC).

**The detection logic is genuinely good and it still didn't fire.**
`metric_zeek_ingest_lag_seconds()` (`slo_metrics.py:520`) is in `BREACH_IF_NA`
(line 249), so no-data is a breach rather than a null — and its docstring
names this precise scenario: *"that's exactly how a real Zeek outage went
undetected until manual investigation found it."* The rule was written from
the postmortem of the previous instance of this same outage.

**Why it missed anyway — a three-way shared fate:**
1. The **runner** is inside the failure domain (unit needs `docker` to start — #550's subject).
2. The **data source** is inside the failure domain: the metric is an ES query (`POST /logstash-security-*/_search`, line 552), and ES is a Docker container. Docker down -> the query cannot resolve -> `MetricUnavailable`.
3. The **transport** is unset (`NTFY_TOPIC`).

#550 fixes leg 1 only. Post-fix the unit reaches `ExecStart`, the metric raises
`MetricUnavailable`, that lands in `errors`, and `main()` correctly routes
errors to the alert branch — which then evaluates `and NTFY_TOPIC` to false and
returns silently. **Legs 2 and 3 keep the outcome at zero signal.**

`capture_iface_preflight.sh` (PR #551) improves observability by converting an
unusable interface into a terminal `failed` state via
`RestartPreventExitStatus=78`, instead of an `active`-reporting crash loop. But
nothing on this host polls unit state, so `failed` is still only visible to a
human who runs `systemctl` by hand.

**Proposed detection — two independent legs, deliberately outside the Docker
failure domain:**

*(a) Unit-failure notifier — pseudocode, systemd:*
```
# configs/systemd/soc-alert@.service   (new, Type=oneshot, template)
ExecStart=/home/tjlam/projects/Suburban-SOC/scripts/setup/soc_alert.sh "unit-failed" "%i"
# then on each of the 6 units:
OnFailure=soc-alert@%n.service
```
`soc_alert.sh` posts to ntfy using only curl + `.env` — no Docker, no ES.

*(b) Deploy `stack_health.sh` on a timer.* It already checks container liveness
via `docker ps` (line 34) and degrades correctly when `docker` is off PATH:
absent binary -> container reported down -> alert. It needs no new logic, only
installation.

**Required telemetry:** none new. (a) uses systemd's own state machine, (b) uses
`docker ps` + local HTTP. Both work with ES fully down.

**Evasion resistance:** (a) catches any unit reaching `failed`, including
scenarios 2 and 3, and is immune to renaming/relocating a binary. It does
**not** catch `zeek-host-capture`'s `Restart=always` crash-loop or its `active
(running)` wedge, because neither reaches `failed` — that residue is what (b)
and the ingest-lag metric cover, and it is why both legs are needed. An
attacker who stops the timer units themselves defeats (b); `OnFailure=` does
not fire on a clean `systemctl stop` either. Residual gap: deliberate,
graceful disablement of the monitor. Closing that needs the journal-shipping
work in Gap 3.

**Build effort:** Low (a: one new unit + 6 one-line additions). Low (b: install
existing script).

### Gap 2 — Persistent unit failure is invisible (T1562.001) — P1

**What the attacker does:** with the service UID, write a foreign cert over
`/var/lib/suburban-soc-slo/ca.crt`. Every subsequent run: `es_ca_cache.sh
restore` installs it -> `verify_ca_fingerprint.sh` mismatches -> `rm -f` the
`/run` copy -> `exit 1` -> unit dead before `ExecStart`. `verify` only deletes
the `/run` copy; the `/var/lib` cache is not in its argv, so the condition is
permanent and self-perpetuating. Cost to the attacker: one file write.
Result: the SOC's entire measurement lane, permanently, silently.

**Validated, not assumed.** Simulated against the real script with two
generated CAs (`scratchpad/ca-test/`, benign, local-only):

```
run 1: [FATAL] ES CA fingerprint changed: expected 6C:E3:2B:...:F0:4A, got CB:23:AB:...:D8:D0
       exit=1 ; ca.crt -> deleted
run 2 (next timer tick, cache re-supplies the same cert):
       [FATAL] ... identical ... exit=1 ; pin file unchanged
```

Confirmed: the loop does not self-heal, and the pin is never rewritten.

**Note on the accepted MEDIUM 1 fix:** fingerprint-checking the cache in both
verbs makes the *stale-cache operator* variant self-heal, but does **not**
close the attacker variant. With that fix, `restore` refuses the poisoned
cache -> `/run/ca.crt` is absent -> `verify_ca_fingerprint.sh:50-53` returns
`exit 0` ("missing or empty, nothing to verify") -> `ExecStart` runs with
`ES_CA` pointing at a nonexistent file -> `requests` raises on every call ->
all 15 metrics `ERROR(unmeasurable)` -> `sys.exit(3)`. **The unit converts from
hard-fail to soft-fail and the availability outcome is identical — still no
metrics, still silent.** Which is precisely the state the live host is in
today for a different reason (the 401).

**Why current detections miss it:** no `OnFailure=`, nothing polls
`systemctl is-failed`, journal not shipped. The `[FATAL]` line is well-written
and reaches no consumer.

**Proposed detection:** Gap 1's `OnFailure=` handler covers the hard-fail
directly. The soft-fail variant (`exit 3`, unit `failed` under
`SuccessExitStatus=0 2`) is also covered — `exit 3` is not in the forgiven set,
so the unit does reach `failed` and does trigger `OnFailure=`. **One control
covers both variants**, which is what makes it the best value in this backlog.

Add a staleness backstop so a monitor that stops running entirely is still
noticed — deliberately *not* self-hosted inside `slo_metrics.py`:
```
# in stack_health.sh, alongside the existing container checks
newest = max(@timestamp) of soc-slo-metrics
if now - newest > 60m: DOWN("slo-metrics stale")
```
This is the check that would have caught the 20-day freeze on 2026-08-17.

**Required telemetry:** systemd unit state (local); one ES query for the
staleness backstop.
**Evasion resistance:** catches every exit path that reaches `failed`. Misses a
clean `systemctl stop`/`disable` and misses masking the handler unit itself.
**Build effort:** Low.

### Gap 3 — CA-swap attempt is prevented but not reported (T1553.004 / T1557) — P2

**Prevention is real and was validated** (the run above): the pin refuses the
substituted cert and deletes it. `slo_metrics.py:265` sets
`ES_VERIFY = ES_CA if ES_CA else True`, so there is no silent-insecure
fallback. Credit where due — this control does its job.

**Detection is absent.** The `[FATAL] ES CA fingerprint changed` line
(`verify_ca_fingerprint.sh:77`) goes to stderr -> journal -> rsyslog ->
`/var/log/syslog` -> **stops there**, because nothing ships it. No index, no
rule, no alert. An attacker learns their attempt was refused; the defender
learns nothing. The one signal that *does* escape is second-order: the unit
fails, so Gap 1's `OnFailure=` handler fires — but it reports "unit failed",
not "someone swapped your trust anchor". Those warrant very different
response.

**Proposed detection — Sigma, matching the repo's existing format:**
```yaml
title: SOC ES CA fingerprint mismatch - trust anchor substitution attempt
status: experimental
logsource:
    product: linux
    service: syslog
detection:
    selection:
        message|contains: '[FATAL] ES CA fingerprint changed'
    condition: selection
level: high
tags:
    - attack.t1553.004
    - attack.t1557
falsepositives:
    - Deliberate CA rotation where the operator did not delete the pin file first
```
Companion rule on `'[FATAL] could not compute a SHA-256 fingerprint'`
(`verify_ca_fingerprint.sh:64`) — that fires on a truncated or corrupted cert,
which is the tampering variant that does not produce a clean mismatch.

**Required telemetry (prerequisite — this rule cannot run today):** a Filebeat
`filestream` input on `/var/log/syslog`, plus a Logstash branch to stamp
`event.dataset`. Recommended over a `journald` input: rsyslog already captures
the content (proven — 205 `slo-metrics` lines present), and the `filestream`
pattern is already used twice in `configs/network/filebeat.yml`, so it copies
an in-repo working shape rather than introducing a new input type whose
behaviour across the pinned Filebeat version I have not verified here.

**Evasion resistance:** string-matching a message this SOC emits itself is
sound — an attacker cannot suppress it without stopping the unit (which Gap 1
catches) or tampering with the script (which changes a repo file). Weakness:
if the wording of `verify_ca_fingerprint.sh:77` is ever edited, the rule
silently stops matching. Add a test asserting the rule's string is present in
the script, the same way `test_es_ca_fingerprint_pinning.py` pins other
invariants.

**Build effort:** Medium — the rule is trivial; the log-shipping prerequisite
(Filebeat input + Logstash branch + index template + ECS mapping) is the work.

### Gap 4 — Compactor credentials have no pin and no monitor (T1553.004 / T1557) — P3

**Claim verified — neither compactor pins anything:**
```
configs/systemd/checkpoints-compact.service:94   ExecStartPre=-/usr/bin/docker cp elasticsearch:.../ca.crt /run/suburban-soc-checkpoints-compact/ca.crt
configs/systemd/threat-intel-compact.service:81  ExecStartPre=-/usr/bin/docker cp elasticsearch:.../ca.crt /run/suburban-soc-threat-intel-compact/ca.crt
```
No `verify_ca_fingerprint.sh` invocation in either file. Compare the sibling
that does have one:
```
configs/systemd/intel-refresh.service:122        ExecStartPre=-/usr/bin/bash .../verify_ca_fingerprint.sh /run/suburban-soc-intel/ca.crt /var/lib/suburban-soc-intel/ca_fingerprint.sha256
```
So of the four ES-CA-extracting units, two pin and two do not. An attacker
substituting the CA inside the `elasticsearch` container therefore gets these
two units to trust an attacker-controlled anchor and captures
`AGENT_CHECKPOINTS_COMPACTOR_PASSWORD` and `THREAT_INTEL_COMPACTOR_PASSWORD` in
the resulting TLS session — the latter being a **delete-capable** credential on
`threat-intel-indicators` (558 indicators live).

Worth noting even on `intel-refresh.service`, the pin call is `-`-prefixed, so
a mismatch does not fail that unit — `verify` deletes the cert and the run
degrades quietly. Prevention holds (no insecure fallback); notification does
not.

**Materially reduced live exposure:** neither compactor is installed on this
host. `systemctl list-unit-files` shows only `intel-refresh`, `slo-metrics` and
`zeek-host-capture`; there are no `checkpoints-compact` or `threat-intel-compact`
units, and `list-timers` shows only `slo-metrics.timer` and `intel-refresh.timer`.
**The exposure is latent in the repo, not live on this host** — which is exactly
why this is P3 and not P1.

**Compensating detection, on paper only:** `metric_intel_indicator_count_drop_pct()`
(`slo_metrics.py:1702`) exists specifically to catch a wipe via the
`threat_intel_compactor` credential — a genuinely good piece of design, and it
covers a consequence the retired Watcher never covered. But it runs in the dead
`slo-metrics` lane (currently `ERROR(unmeasurable)`), and it covers only the
intel index — nothing at all watches the checkpoints credential.

**Proposed fix — prevention first, one line per unit,** copying
`intel-refresh.service:122` verbatim with the paths adjusted:
```
ExecStartPre=-/usr/bin/bash .../verify_ca_fingerprint.sh /run/suburban-soc-checkpoints-compact/ca.crt /var/lib/suburban-soc-checkpoints-compact/ca_fingerprint.sha256
```
Detection then comes free from Gap 3's rule, since both units would emit the
same `[FATAL]` string.

**Build effort:** Low (2 lines + `StateDirectory=` on each).
**Priority rationale:** highest evasion risk of the four (no control exists at
all), but not currently reachable on this host.

## Prioritized remediation backlog

Sequenced for one operator. **The order matters — items 1 and 2 are coupled.**

**P1a — Resync the `slo_metrics` ES credential (owner action, do FIRST).**
`SLO_METRICS_PASSWORD` in `scripts/setup/.env` no longer matches ES; every
metric is `ERROR(unmeasurable)` and `soc-slo-metrics` has been frozen 20 days.
*Effort: minutes.* Requires a human to rotate a live stack credential.

**P1b — Set `NTFY_TOPIC` in `scripts/setup/.env` (do SECOND, not first).**
One key. Unblocks 100% of alert delivery for both `slo_metrics.py:1969` and
`stack_health.sh:76`. Every other item in this backlog is decoration until this
lands. *Effort: minutes.*

> **Ordering is load-bearing.** Setting `NTFY_TOPIC` while the 401 persists
> produces a high-priority push listing 15 unmeasurable metrics every 15
> minutes — 96 per day. The predictable operator response is to mute the topic,
> which re-creates the exact silence this whole exercise exists to fix, except
> now with a false belief that alerting works. Fix P1a first, confirm one clean
> run, then set the topic.

**P2 — Add `OnFailure=` to all six units + a Docker/ES-independent notifier.**
The single highest-leverage structural item: one new template unit plus six
one-line additions covers Gaps 1, 2 and the second-order signal in 3, and works
with the entire container stack down. *Effort: Low.*

**P3 — Install `stack_health.sh` on a systemd timer, plus an
`soc-slo-metrics` staleness check.** The control already exists and is already
correct; it has simply never been deployed. Prefer a timer over
`configs/monitoring/reliability.cron` for consistency with #222's cron->timer
precedent. Add the staleness check that would have caught the 2026-08-17
freeze. *Effort: Low.*

**P4 — Ship `/var/log/syslog` to ES, then author the two Sigma rules.**
Unlocks Gaps 3 and 4 and gives this SOC its first Linux `T1562.001` visibility.
Largest lift; do not start it before P1-P3. *Effort: Medium, multi-session.*

**P5 — Pin the CA in both compactor units.** Two lines. Fold into an existing
hardening issue rather than opening its own — the units are not installed, so

## Validated detections — what the blue team can trust

Tested and confirmed working. This list is short, and that is the finding.

1. **TOFU CA pinning — `scripts/setup/verify_ca_fingerprint.sh`.** Empirically validated against two generated CAs: mismatch refused, `exit 1`, cert deleted, pin not overwritten, behaviour repeatable across runs. As a *preventive* control this works exactly as documented. It is not a detection and must not be counted as one.
2. **No silent-insecure TLS fallback.** `ES_VERIFY = ES_CA if ES_CA else True` (`slo_metrics.py:265`, mirrored at `compact_threat_intel.py:103` and `compact_agent_checkpoints.py:165`). A missing CA raises rather than downgrading. Verified by reading all three call sites.
3. **`metric_zeek_ingest_lag_seconds()` logic (`slo_metrics.py:520`) is correct.** Filtering to `event.dataset:zeek.*` genuinely distinguishes "Zeek is silent" from "something else is still writing", and `BREACH_IF_NA` (line 249) correctly treats no-data as breach. The 2026-09-06 09:06 run classified the lane as `BREACH(no-data)` accurately. **The logic is not the problem — delivery is.** Worth repeating as a pattern: per-source liveness beats aggregate liveness.
4. **Error-path alerting is correctly wired in `main()`.** `if (breaches or errors)` at line 1969 means an unmeasurable metric is not allowed to be silent (#216). Correct design, currently defeated only by the unset topic.
5. **`RestartPreventExitStatus=78` / `capture_iface_preflight.sh` (PR #551).** Separating permanent config errors from transient Docker-not-up-yet by exit code, so `systemctl is-active` reports the truth, is the right shape. It improves *observability*; it is not yet *detection*, because nothing polls unit state — P2 and P3 are what convert it.

### Partial disagreement — the MEDIUM 1 "correction"

The report states that the cache fingerprint-check "does not close scenario 2's
attacker variant" and that "the availability outcome is identical and equally
silent". That is true **only under the current condition that `NTFY_TOPIC` is
unset** — which is the report's own separate P1b gap. It is contingent, not
intrinsic, and three things do change:

1. **The attacker's persistence is removed.** `restore` deletes the poisoned
   cache. The next run that can reach the Docker engine re-caches the real CA
   and the unit self-heals. Pre-fix the poison survived indefinitely, because
   `verify_ca_fingerprint.sh` only ever deletes the `/run` copy.
2. **`ExecStart` runs.** `slo_metrics.py` executes, locally-computable metrics
   still print, and `slo_metrics.py:1969` `if (breaches or errors) and
   NTFY_TOPIC` becomes reachable — an alert path that depends on neither Docker
   nor Elasticsearch. Pre-fix the unit died at `ExecStartPre` and no alert of
   any kind was possible from inside it.
3. **The journal names both fingerprints** (`no longer matches the pin (cached
   C0:01:… pinned AE:BE:…)`) rather than a generic ExecStartPre failure.

The valid kernel is narrower than stated: in the both-conditions corner case
(poisoned cache **and** Docker unavailable) the run reports a TLS CA-bundle
error, which is the misleading error the cache exists to eliminate. That is a
diagnostic-quality regression in a corner case, mitigated by the explicit WARN
line immediately preceding it in the same journal. **No change made to the
fix.** The report's own P1b/P2 items are what actually close scenario 2.
